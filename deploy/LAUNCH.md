# Установка на sette.su

## Фактический статус на 01.10.2026

Сайт проверен локально. Никакие файлы действующего sette.su не изменены, DNS не переключался, реальная заявка в Битрикс24 не отправлялась. Содержимое репозитория на GitHub и исходной папки совпало по коммиту 870bc3f.

Старый сайт отвечает как WordPress, сервер — openresty, в HTTP-заголовке указан PHP/7.4.33. Это наблюдение по публичному ответу, не подтверждение конфигурации панели. Перед внедрением проверить версию PHP на самом хостинге и доступные поддерживаемые версии с учётом старого WordPress. Не менять версию всему WordPress без проверки совместимости плагинов.

## Нужные данные

1. Панель хостинга или доступ к файлам сайта, настройке главного index/rewrite, резервной копии файлов и базы. Административный доступ WordPress полезен для проверки старых страниц, но его одного может быть недостаточно.
2. Входящий вебхук существующего Битрикс24 с правом создания лидов CRM. Проверить, использует ли портал лиды или работает без них (в таком случае понадобится другой метод, например создание сделки с контактом). Вебхук сохранить в приватный файл на сервере, не в Git, HTML или чат.
3. Юридическое лицо — владелец сайта и оператор данных: полное и сокращённое наименование, ИНН, ОГРН, юридический адрес, контактная почта. Утверждённые тексты политики и согласий либо данные для завершения исходных шаблонов. Даты/номера внутренних приказов, ответственный, сроки хранения и место обработки нельзя достоверно определить из прототипа.
4. Отдел продаж должен подтвердить сроки, застройщиков, проценты готовности, координаты с `approx: true`, контакты и актуальные планировки. Исходные данные сохранены, но не переутверждены.

## Безопасная последовательность

1. В панели сделать резервную копию **файлов и базы WordPress**, сохранить текущие rewrite/index-настройки. Проверить, что восстановление доступно.
2. Развернуть предварительную версию на закрытом от индексации тестовом адресе того же хостинга. Не удалять WordPress и `wp-content/uploads`: старые страницы с планировками и документами остаются нужны. Сверить пути из `deploy/legacy-routes.json` и текущую карту сайта.
3. Настроить выполнение PHP для `/api/lead.php`, наличие расширений cURL и mbstring, доверенного CA для HTTPS. GET обработчика должен возвращать JSON с кодом 405, а не PHP-исходник.
4. Скопировать пример конфигурации **вне веб-корня**. По умолчанию обработчик ищет `../../private/sette-config.php` относительно `api/`; при другой структуре задать переменную `SETTE_CONFIG_FILE`. Указать вебхук, разрешённые origins тестового/боевого сайта, длинную случайную соль и приватный каталог `storage`. Права: файл 0600, каталог 0700, владелец — пользователь PHP. Значения consent_version должны совпадать с утверждёнными текстами и legal.js.
5. Отправить согласованную тестовую заявку и проверить её появление в Битрикс24, телефон, выбранный ЖК, UTM и версии согласий. Затем проверить ошибку доставки на тестовом адресе. Локальные имитации не подтверждают работу реального CRM-портала. При сетевом таймауте проверить CRM перед ручной повторной отправкой: сервер мог принять запрос до разрыва соединения.
6. Проверить юридические страницы, старые ссылки, все ЖК, телефоны, HTTPS, мобильный вид, карты, загрузку изображений. Сохранить фактические результаты в `deploy/acceptance.json`: дата, адрес staging, проверяющий, статус резервной копии, результат настоящей заявки, подтверждение данных и документов. Этот файл — журнал приёмки, его нельзя создавать со значением «проверено» заранее.
7. Собрать production-архив `python tools/package.py`. Его публичное содержимое ограничено файлами сайта; в архив не входят Git, tools, deploy, private, артефакты тестов и конфигурация с секретами.
8. Установить поверх публичной главной после сверки конфликтующих имён файлов. На Apache обычно достаточно `DirectoryIndex index.html index.php` или правила только для `^$` перед правилами WordPress; на nginx/openresty порядок index/rewrite настраивается в панели или конфигурации сервера. Выбрать способ по фактическому устройству хостинга. **Не заменять весь .htaccess шаблоном** и не перенаправлять все старые URL на главную.
9. Проверить новую главную, три продаваемых ЖК, юридические страницы, старые URL и реальную доставку формы уже на sette.su. Существующие robots.txt, sitemap, почтовые DNS-записи и WordPress-медиа сохранить, затем обновить карту сайта с учётом новых страниц. Не выкладывать архив preview на боевой адрес.

## Откат и обслуживание

Для отката восстановить прежний порядок index/rewrite и ранее существовавшие файлы из резервной копии; база WordPress в этой миграции не изменяется. Проверить главную и старые страницы. Старые файлы и БД не удалять после первого переключения.

Хостинг должен обеспечивать ротацию журналов согласно утверждённым срокам хранения. Служебные файлы `rate-*.json` и `lead-*.json` нужны для 10-минутного окна; можно удалять только устаревшие файлы старше суток при согласованном обслуживании. Не удалять активные lock-файлы. `consent.log` хранится отдельно по принятой политике.

Все 120 медиафайлов проверены на наличие локально. Внешними остаются карты OSM по мере прокрутки, переходы в Яндекс Карты, страницы старого сайта и ссылки на официальные документы. Новые фотоотчёты добавлять в data.js и в media.js вместе с соответствующими локальными файлами.
